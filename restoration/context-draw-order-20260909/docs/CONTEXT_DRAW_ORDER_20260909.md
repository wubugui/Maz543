# 跨上下文绘制顺序与固定源排序实验

完整 goal ACTIVE，16 项整车门槛 OPEN。动态整车显示仍慢，Worker 和本排序均未默认启用。本轮没有降低模型、三角形、贴图、深度或机械计算精度。

## 原排序的实际变化

在完整 `inspect=context-audit` 中增加有限完整绘制记录：按场景遍历登记对象与材质分配 ID，原样记录 renderBufferDirect 的每次调用。实际 ID 不加入输入或绘制序列的 SHA-256，避免把上下文 ID 的数值差异误判为画面差异。大记录保存到隐藏诊断文本，通过 DOM 分段读取到本地，不进入可见层或完整对话正文。首次读取被工具在约 200,000 字符截断，随后按 80,000 字符分段，JSON 成功解析并保存完整约 1,488,000 字符；没有把截断数据用于比较。

最新主线程和 Worker 侧视在相同已记录输入下像素相同，SHA-256 均 `1d0ef1ea90583bb2ee89c9c13eb1586826cc9cfc6ddbdd59ab30ac07382ee165`，但绘制顺序不同。同一 Worker 入口上一轮侧视为 `c3ade12b6ab240e096304501f05d91d39306e10543bc4a95eb286e5b91258f93`，相机、尺寸、AO、噪声和输入子集指纹相同。由此不能把旧差异解释为必然的 Worker 画质变化；当前证据未覆盖所有 shader/纹理输入。

两份完整原排序记录都为 7 个连续通道段、9305 draws、21,582,915 三角形。阴影与后处理段相同；透射背景、主颜色和法线段成员完全相同而顺序不同。第一个不同调用是相同 D12_cast_aluminium 材质下 R1/R6 缸套座先后变化，源材质的相对分配顺序也不同。说明异步分配影响排序，尚未单凭此证明哪一个表面造成旧像素差。

## 受控的源排序

`lib/contextSourceOrder.ts` 仅用于新的“核对固定源顺序”按钮，保留 r183 的 groupOrder、renderOrder、材质成组、materialVariant、精确深度优先级；以源场景遍历顺序决定材质组次序与完全相同深度的对象先后。没有引入 epsilon、改深度、改几何、禁用剔除或减少绘制。后处理独立场景保留原排序。只对该诊断帧设置比较器，finally 恢复原排序；普通预览不变。

实际安装的 WebGLRenderList 受控测试覆盖不透明、透明、透射三类，反转材质/对象创建顺序时原排序确实不同，新排序相同；group/render/variant 和一个 Number.EPSILON 的深度差仍有正确优先级。类型检查及生产构建通过。
