# 静止整车缓存、悬挂零位与精确保形绘制实验

2026-09-09。完整 goal **ACTIVE**，16 项 **OPEN**。本阶段解决了普通入口静止整车持续重绘的两个实际原因；动态整车仍慢，未完成性能或整车机械验收。

## 已启用的修正

`lib/suspension.ts` 的连杆反解保留原有 28 次二分、尺寸、质量、刚度、阻尼、限位、查表间距和内部 480 Hz 子步。旧弹性力直接使用反解角度，零行程仍有约 0.000263728 N 残力。100 秒静止计算出现约 1.17 nm 的车身位移和持续微小速度，实际阴影 uniform 也会变化。

弹性角度现在以同一次反解所得的中性姿态 G0 为零位；车身和车轮的积分按解析静载平衡计算增量力，避免反复相减大静载。离地接触仍钳制为零支承力，内部弹性反力仍抵消。没有添加运动阈值、舍入、减面或冻结微小扰动。

`scripts/verify-suspension-reference.mjs` 与保留的旧源 `work/suspension-reference/baseline-suspension.ts` 对照：参数、刚度及八组行程的几何姿态完全相同；100 秒全自由度精确静止；±1e-12 m 扰动和 1e-12 台架激励仍产生响应。离地总动量与重力冲量差约 1.71e-13 N·s。5 秒、65% 激励的前后轨迹最大车身差约 1.66 nm、轮位差约 0.48 nm、支承力差约 0.000875 N。这是数值参考修正的回归证据，不是原车尺寸、刚度或工厂验收公差。

修正零位后的完整网页 12 帧证明车身姿态、2322 个可见投影网格的世界矩阵和阴影 Float32 姿态均不变，但每帧第一个缓存差异仍是 `BL_Cab_-1_quarterlight_glass` 的材质版本，逐帧增加 32。当前安装的 Three r183 `WebGLRenderer.js` 在透明 DoubleSide 双遍绘制时临时切换 BackSide/FrontSide，每遍递增 version，最后恢复 DoubleSide。因此渲染前快照会把渲染器自身的记账当成下一帧失效。

`DisplayFrameCache.acknowledgeRenderedVersions()` 在成功绘制后仅接纳这种正偶数版本增量：材质仍须透明、DoubleSide、非 forceSinglePass，且材质及共享对象不能带自定义绘制回调。其他全部数值继续按 Object.is 比较。程序后续 needsUpdate、透明度、属性版本、相机或 1e-30 位移仍触发绘制；异常奇数增量和自定义回调采用保守重绘。玻璃的双面绘制、透明度和 shader 未改动。对应测试在 `scripts/verify-rendered-material-versions.mjs`。

## 实际网页结果

证据在 `outputs/suspension-reference/`：

- `whole-profile.json`：仅修正悬挂后，仍因玻璃版本每帧重绘，9305 calls / 21,582,915 累计三角形，阴影姿态变化为零。
- `whole-cached-profile.json`：加入材质版本记账修正后，完整 8868 实例的连续 12 帧全部 `rendered:false`、`cacheChange:null`，机械时间约 38.375 → 38.692 s，积压为零。线程工作约 12.8–24.2 ms，不能称为动态整车 FPS。
- `door-profile.json` 及 AX：右前门实际到达 99°，操作恢复绘制，之后 11 个样本重新缓存。采样并未完整覆盖门运动全过程，不能用它声称平滑门动画已经解决。
- 普通无查询参数入口 `http://localhost:3000/` 装配 8868 实例后显示“画面已缓存”，完整车辆可见，独立机械计算 240 Hz、积压零。实际截图已在任务工具输出中检查；AX 保存在 `ordinary-idle-ax.txt`。
- 普通入口点击“八轮独立悬架”，65% 激励下 I 左机构持续更新，切换扭杆/减振器内构成功。两个时刻的行程为 +13 / −28 mm，支承力 29.1 / 19.1 kN，车身起伏 +18 / −32 mm；读取和截图并非同一时刻，截图读数可不同。有限单轮检查显示约 4 FPS，不是整车性能。
- 用户界面“暂停并检查”后，内构静止画面重新缓存，整体机械时钟继续推进。`ordinary-suspension-paused-ax.txt` 保留现场状态。没有把可视暂停加入求解器的自动阈值。

默认仍使用普通主线程显示；完整 Render Worker 和 native RAF 仍为开发参数。以上修正在两条显示路径共享同一实现。

## 未接受的优化实验

`ShadowPoseProbe` 只在手动有限逐帧诊断中比较实际 Float32 阴影姿态，不改变阴影。修正悬挂前，2322 个可见投影网格中每帧 2316 个世界矩阵变化、904 个阴影 Float32 矩阵变化。因此当时不能直接缓存整张阴影图。未接受的整图缓存草案移至 `work/shadow-cache/directionalShadowCache.ts.prototype`，不在编译/运行路径；该草案旧类型错误日志保留，不应标为已通过或已启用。零位修正后静止整车直接缓存最终画面；运动状态的阴影仍每帧更新。

新增 `lib/exactBatchMatrices.ts` 和开发入口 `inspect=batch-exact-audit`，对批量绘制逐实例输入原绘制的 CPU model-view/normal Float32 矩阵，深度和 GTAO 法线材质也使用相应输入。源材质保留，克隆材质接收源更新，原几何/选择/导出不变。小场景矩阵载荷逐位一致测试通过。

但完整网页核对仍失败：1906 个实例组成 51 批，2558 几何、80,659,352 属性分量、18,507,990 索引复制差异为零；两边都绘制 21,582,915 个累计三角形，calls 9305 → 1885；1212×773 实际画面仍有 **332 个像素不同、最大通道差 141**，读回错误均为零。首次同步候选 3382.4 ms、基线 2316 ms，包含编译/读回，不能作为稳定帧率。额外内存约 393 MB。

因此精确矩阵载荷不等于整幅画面相同。绘制排序、剔除及 shader 编译等因素尚未定位，**批量绘制没有默认启用**。`outputs/exact-batch/whole-audit.json` 保留失败证据，不重跑来挑选更好的计时。
