# 交互帧与静止精修（2026-09-28）

完整 goal ACTIVE，整车 16 项验收 OPEN。本轮只改显示调度，没有改任何几何、贴图、材质参数、机械求解或导出内容。

## 先纠正此前的测量口径

此前 0.3–1 FPS 的记录全部来自 **Microsoft Basic Render Driver（软件渲染）**。本机实际有 NVIDIA GeForce GTX 970（4 GB），当前内置浏览器与独立 Chrome 都走 `ANGLE (NVIDIA GeForce GTX 970, D3D11)`，而且 `EXT_disjoint_timer_query_webgl2` 可用，可以拿到真实 GPU 时间。

`frame-profile` 里反复出现的 `gpuMs 974` 只是某一次**首帧着色器编译**时的旧读数：计时查询每 30 帧才发一次，没有新结果时一直显示旧值。同一帧第二次绘制实测只要 GPU 28 ms / CPU 24 ms。

## 真实瓶颈（GTX 970，927×833，完整整车，外观视图）

| 通道组合 | 调用数 | CPU 提交 | GPU |
| --- | ---: | ---: | ---: |
| 颜色 + 玻璃透射预绘制 | 4655 | 24 ms | 28 ms |
| + GTAO 法线/AO | 6983 | 44 ms | 51 ms |
| + 阴影重绘 | 9305 | ~50 ms | ~50 ms |

- 每个通道都把约 2323 个可见网格重画一遍。只有 8 块车窗玻璃带透射，却为此把全部不透明件多画了一遍。
- 画面缓存的逐项比较每帧约 8 ms，阴影缓存的签名每帧约 11.5 ms。它们在"反正要重画"的交互帧里是纯开销。
- GPU 时间几乎不随分辨率变化（纵剖 3043 件：2146×858 为 32.7 ms，1073×429 为 29 ms），说明卡在逐次绘制上，不是像素填充。降分辨率没用。

## 改动

`lib/vehicleViewport.ts`，普通入口默认启用；`?quality=full` 每帧都走原完整路径。

1. **交互帧**：镜头或机构在变化时，照常绘制同样的几何、材质和姿态，只推迟三类整场景重画：
   - GTAO 暂停；
   - 透射玻璃临时换成同不透明度、同粗糙度、同反射的混合玻璃，漫反射按 `1 - transmission` 缩放，省掉透射预绘制；
   - 只有镜头动时不重画阴影（定向光阴影与主相机无关）。机构运动时，阴影最多每 125 ms 刷新一次。主光源或阴影相机一变，立即刷新。
2. **静止精修**：最后一次变化 180 ms 后，按原完整路径（精确阴影缓存、GTAO、透射玻璃）补一帧，之后照旧走静止缓存。交互帧里刷新过阴影，就让阴影缓存失效，防止姿态回到旧签名时误用深度图。
3. **画面缓存快速判定**（`lib/displayFrameCache.ts`）：镜头一变，直接判"需要重画"，跳过全场景比较，下一次完整比较重新建立基线。标准/物理材质只检查其声明的 23 个贴图槽，其他材质仍全量扫描属性。
4. **交互帧微小零件剔除**：包围球投影半径小于 1.5 像素的网格（整车透视视角下 3043 个里约 1550 个），只在交互帧里跳过，精修帧全部绘制。统计是每帧对可见网格做一次包围球投影，约 3000 次，开销可忽略。
5. **已撤回：变速箱"封闭内构"隐藏**。起初按"包围盒/回转包络在 `TX_housing` 内"在实心外观下隐藏约 1400 个内件。同姿态像素对照在俯视、后视下出现实际差异（俯视 597 像素差 >8，最大 184）：`TX_housing` 是有大开口的框架，不是封闭壳体，从上方能直接看到离合器鼓。所以撤掉了这项，外观视图保持原来的 2323 个可见件；流畅度改由交互帧的微小零件剔除保证。

## 像素核对（同一页面、同一姿态，侧视，1983×985 截图的画布区域）

- 自适应路径静止精修帧与原完整路径：**0 像素差**。
- 变速箱封闭内构隐藏：俯视、后视出现实际差异，已撤回（见改动第 5 条）。
- 精修帧逐像素比对是在机构完全静止时做的。停机后变速箱行星轮还在惯性转动时，画面一直处于交互帧，此时和完整路径本来就不同，不能拿来对比。
- 交互帧与完整帧：110656 像素不同，最大通道差 30，来自暂缓的 GTAO 和近似玻璃，停下即恢复。

开发句柄：`?debug-handle=1` 暴露 `window.__maz`（renderer/scene/camera/composer 等）和 `setAdaptive(bool)`，用于同姿态 A/B。仅开发构建。

## 仍未解决

- 透视、纵剖在发动机运转时约 51–52 FPS，p95 偶有 33 ms，来自每帧全量缓存比对（约 3000 件）和阴影刷新。进一步提升的方向：把同材质静止件合批（`BatchedMesh` 用贴图存矩阵，省掉逐件 uniform 与状态切换）。可以只在交互帧启用，精修帧仍走原路径。已有的 `DisplayBatches` 精确矩阵实验可以复用，但只在交互帧用，不需要逐像素证明。
- 发动机停机后变速箱行星轮仍按惯性转动。只要它可见（打开变速机构时），画面就一直处于交互帧、不会精修。这是机械状态本身，不是显示问题。
- 本机显存 4 GB，另有其他进程占用约 0.8–1.4 GB。整车载入后约 1.9 GB，勿同时开多份整车页面。

## 独立审查后的修正（同日）

一个只读审查 agent 核对了实现，下列问题已修：

1. **镜头阻尼尾巴**：OrbitControls 的阻尼每帧乘 0.92，松手后几秒内仍有肉眼不可见的微小位移，精修帧迟迟不来。现在 `orbit.update()` 返回"无显著变化"、且没有视角过渡时，关阻尼结算一次剩余位移（仅自适应路径）。CDP 真实鼠标拖拽实测：松手后镜头最后一次变化从 **6588 ms 降到 1334 ms**。
2. **交互玻璃重复编译**：每次精修绘制源玻璃都会抬高它的版本号，旧实现因此重建克隆、重编着色器。现在每个源材质只保留一个克隆，版本变化时用 `copy` 原地同步，线框/可见/不透明度每帧同步。
3. **转镜头时机构阴影冻结**：快速判定帧看不到机构变化。现在保留最近一次完整比较得出的 `mechanismActive`，镜头快速判定期间也按 125 ms 刷新阴影。
4. **镜头停下后误算机构变化**：没有基线时的完整比较标记为 `rebase`，不再算作机构变化，避免多一次交互阴影重画和精修时的重复阴影。透视模式下交互帧会抬高幽灵材质版本号，精修时阴影缓存仍会多画一次，只影响性能，保留。
5. **光源变化时阴影缺微小件**：主光源或阴影相机变化触发的刷新帧，不剔除投射阴影的件。
6. **异常安全**：玻璃替换、微小件隐藏都放进 `try`，`finally` 恢复并处理阴影缓存失效。

回归（1563×858）：外观转镜头 59.8，发动机运转 60，运转同时转镜头 59，发动机单独查看 60/60 FPS。

## 待核实的观察

- 基准测试中，有一次在发动机显示 0 RPM 时，看到冷却风扇电枢 `COOL_armature_0`（转角 = −曲轴角 × fanRatio）逐帧变化，画面因此一直处于交互帧。在全新加载、未启动的页面上复查：电枢和曲轴转角 2 秒内保持为 0，**未复现**。那次很可能是同一页面前面的测试启动过发动机后的滑行状态。留作记录，不当成缺陷。
- `DisplayFrameCache` 用 `Object.is` 比较，会把矩阵元素在 0 与 -0 之间的翻转当成变化。这是既有行为，本轮未改；只有在它导致实际多余重绘时才值得处理。
